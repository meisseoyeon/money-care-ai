# 초기 준비 재실행·동시 실행·롤백

## 처리 원칙

같은 작업을 다시 실행해도 결과를 덧붙이거나 최초 입력을 바꾸지 않습니다. 새로운 날짜나 변경된 입력으로 새 계산을 하려면 새 실행 ID를 사용합니다.

| 구분 | 중복을 구분하는 키 |
|---|---|
| 기준 통계 | 사용자·한국 날짜·계산 버전 |
| 생활비 입력 | 사용자·기준 시각·계산 버전 |
| 생활비 결과 | 입력 스냅샷 ID |
| 초기 준비 실행 | 사용자·실행 ID·통계 버전·생활비 버전 |

기존 계산 테이블의 기본키·유일 제약·`ON CONFLICT DO NOTHING`과 사용자 행 잠금을 유지합니다. V7에서 `initialization_runs`를 추가해 실행 ID와 최초 결과를 연결합니다. 실행 기록은 결과를 모두 준비한 뒤 같은 트랜잭션에서 저장하므로 완료된 작업만 남습니다. 별도 진행 중·실패 행은 만들지 않습니다.

## 같은 실행과 새로운 실행의 차이

```python
from app.demo.initialization import ensure_initial_preparation
from app.db.session import session_factory

run_id = "init:example-unique-job"  # 실제 작업마다 고유하게 생성하고 재시도에서는 재사용

with session_factory()() as db, db.begin():
    first = ensure_initial_preparation(db, user_id="user1", run_id=run_id)

with session_factory()() as db, db.begin():
    retry = ensure_initial_preparation(db, user_id="user1", run_id=run_id)
    assert retry == first
```

완료 기록이 있으면 현재 잔액이나 날짜가 바뀌었더라도 같은 실행 ID·버전은 최초 결과를 반환합니다. 새 계산에는 새 실행 ID를 전달합니다. 새 실행이라도 오늘의 현재 입력이 기존 입력과 같으면 계산 결과는 재사용하고 새 실행과 결과의 연결만 기록합니다.

이 연결 기록이 없으면, 다른 실행이 만든 스냅샷을 재사용한 작업이 나중에 재시도될 때 최초 결과를 찾지 못할 수 있습니다. V7은 이 경우에도 실행 ID로 원래 결과를 정확히 찾도록 합니다.

로그인은 매번 새 실행 ID와 새 인증 세션을 사용합니다. 따라서 같은 브라우저나 다른 브라우저에서 다시 로그인하면 토큰은 별도로 발급되지만 입력이 같으면 통계·생활비 결과는 중복 생성되지 않습니다. 로그인 요청 자체의 토큰·세션을 하나로 합치는 기능은 아닙니다.

계산 버전은 실행 키에 포함됩니다. 새 규칙으로 다시 계산할 때 기존 결과를 덮어쓰지 않습니다. 날짜를 넘겨 같은 실행 ID를 재시도해도 최초 날짜를 유지합니다.

## 동시 실행

`ensure_initial_preparation`은 사용자 행을 `SELECT ... FOR UPDATE`로 잠근 뒤 실행 기록을 확인합니다. 같은 사용자의 두 요청은 순서대로 처리됩니다. 첫 요청이 확정되면 두 번째 요청은 같은 실행 기록이나 현재 입력에 맞는 기존 결과를 재사용합니다.

잠금은 사용자 → 계좌 → 생활비 설정 → 예정 지출 순서를 유지합니다. 변경 서비스도 같은 규칙을 사용해야 합니다. PostgreSQL 기본 격리 수준 READ COMMITTED를 사용하며 최종 commit/rollback은 호출자가 담당합니다. 여러 사용자를 한 번에 처리한다면 사용자별 트랜잭션으로 호출합니다.

DB 기본키가 중복 실행 기록을 차단합니다. 외래키가 기록의 사용자·날짜·버전·스냅샷을 실제 결과에 연결하고, 결과가 없는 완료 기록을 저장하지 못하게 합니다. 실행 기록의 UPDATE도 기존 불변 트리거로 막습니다. 원본 결과가 명시적으로 삭제되면 연결 기록도 함께 삭제되며, 그 뒤 새 로그인에서는 필요한 결과를 다시 준비할 수 있습니다.

## 실패 시 롤백

초기 준비 서비스는 `SAVEPOINT` 안에서 통계·입력·생활비 결과·실행 기록을 생성합니다. 어느 단계에서든 예외가 발생하면 이 작업에서 새로 만든 행을 savepoint까지 롤백하고 예외를 다시 전달합니다. 호출자가 예외를 잡은 뒤 외부 트랜잭션을 commit하더라도 부분 결과가 저장되지 않습니다. 호출자의 savepoint 이전 작업은 유지됩니다.

최종 commit은 계속 호출자 책임입니다. 위 예제처럼 `db.begin()`을 사용하면 예외 시 외부 트랜잭션도 롤백됩니다. 이미 성공한 이전 실행의 결과·세션은 보존합니다.

로그인은 준비뿐 아니라 다음 단계도 하나의 예외 처리 범위에 둡니다.

```text
최신 사용자 상태 확인
→ 초기 준비 savepoint
→ 새 로그인 세션 추가
→ 토큰 생성
→ 응답 값 준비
→ 최종 commit
```

토큰 생성·세션 INSERT·최종 commit에서 실패하면 외부 트랜잭션 전체를 rollback하고 토큰을 반환하지 않습니다. 예상하지 못한 서버 오류도 rollback한 뒤 내부 로그에 남기고 503으로 안내합니다. 기존 인증 오류는 해당 HTTP 상태를 유지합니다.

DB 연결이 commit 응답 전에 끊기면 서버에서 이미 확정됐는지 알 수 없는 경우가 있습니다. 이 경우 무조건 새 작업을 만들기보다 동일 실행 ID로 다시 확인합니다. 완료 기록이 있으면 최초 결과를 반환하고, 실제로 롤백됐다면 새로 준비합니다. 자동 무한 재시도는 추가하지 않았습니다.

## 같은 DB 세션에서 재시도

Core INSERT 후 읽은 ORM 객체는 savepoint 롤백 이후 메모리에 남을 수 있습니다. 실행 기록과 기준 통계 조회는 identity map의 존재만으로 저장 여부를 판단하지 않고 DB를 다시 조회합니다. 실제 외래키 오류 후 같은 DB 세션·외부 트랜잭션에서 재시도하는 테스트로 검증합니다.

## 적용과 검증

기존 V1~V6은 수정하지 않았습니다. 팀원이 코드를 받으면 API 실행 전에 다음을 수행합니다.

```powershell
docker compose -f .\compose.yaml run --rm flyway migrate
```

현재 개발 DB에는 V7을 적용했습니다. 계좌·거래·잔액을 변경하거나 초기화하지 않는 테이블 추가 마이그레이션입니다.

테스트용 pgvector PostgreSQL 접속 주소를 `DEMO_TEST_DATABASE_URL`에 설정하고 `backend`에서 실행합니다.

```powershell
..\.venv\Scripts\python.exe -m unittest tests.test_login_initialization -v
```

20개 테스트가 초기 SQL 사용자 로그인, 재실행·현재 입력 재사용, 동시 로그인·동일 실행, 날짜 변경, 누락 복구, 단계별 실패, 실제 외래키 오류, 같은 세션 재시도, 토큰 실패, 세션 flush 이후 commit 실패, 실행 기록의 중복·수정 금지를 검증합니다. 별도 테스트 스키마만 사용하며 서비스 DB를 초기화하지 않습니다.
