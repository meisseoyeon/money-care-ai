# 송금 준비 검사와 송금 후 생활비 저장

## 구현 흐름

```text
인증·모니터링 동의 확인
→ 사용자 잠금
→ 이미 완료된 동일 송금 요청인지 확인
→ 오늘 통계·유효한 생활비 결과 검사
→ 실제 계좌 잔액 검증
→ 잔액 차감·거래 INSERT
→ 새 잔액의 생활비 입력 스냅샷 저장
→ 생활비 결과 계산·저장
→ 날짜 경계 확인
→ 한 번에 commit
```

`transactions/service.py`가 송금 전체 트랜잭션을 관리하고, `transactions/budgets.py`가 기존 기준 통계·생활비 서비스를 연결합니다. 탐지·알림·설명 로직을 호출하거나 생성하지 않습니다.

## 준비 상태 검사

새 송금은 다음 조건을 모두 만족해야 합니다.

- 기존 유효 로그인과 모니터링 동의가 있음.
- 현재 한국 날짜·현재 계산 버전의 기준 통계가 있음.
- 현재 버전의 최신 생활비 입력에 계산 결과가 있음.
- 입력 날짜와 계좌별 잔액·잔액 시각·설정·예정 지출이 현재 상태와 같음.
- 받는 사람이 유효하고 금액이 실제 계좌 잔액을 넘지 않음.

준비가 없거나 오래됐다면 409로 거절하며 새 통계나 초기 계정을 자동 생성하지 않습니다. 다시 로그인해 필요한 결과를 준비한 뒤 시도합니다. 프론트 버튼을 우회해 API를 직접 호출해도 같은 검사를 적용합니다.

부족 생활비가 예상된다는 이유만으로 송금을 거절하지 않습니다. 실제 송금 가능 잔액 검증과 생활비 부족 계산은 별개입니다. 부족 결과를 탐지·알림으로 만드는 작업은 와우 담당입니다.

## 송금 후 계산

잔액·거래를 flush한 뒤 DB에서 실제 변경된 입력을 읽습니다. 기존 공통 스냅샷·계산·저장 함수를 사용하며 commit은 송금 서비스에서만 합니다.

예를 들어 잔액 80만 원, 남은 기간 20일, 하루 생활비 2만 원, 예정 지출 15만 원에서 30만 원을 보내면 다음과 같습니다.

```text
송금 후 잔액      500,000원
예상 생활비       400,000원
예정 지출         150,000원
여유 금액         -50,000원
부족 금액          50,000원
```

기준 통계는 다시 계산하지 않으므로 평가 대상 송금이 당일 기준에 섞이지 않습니다. 준비 검사와 새 스냅샷의 한국 날짜가 달라지면 409로 전부 롤백하고 오늘의 준비를 다시 하도록 안내합니다.

성공 응답의 `forecast`는 `/budget-forecasts/latest`와 동일한 DTO입니다. `id`, `snapshot_id`는 문자열이고 금액·일수는 정수입니다. 성공 직후 최신 조회에서도 같은 결과를 반환하므로 재로그인 없이 프론트의 다음 송금 준비를 이어갈 수 있습니다.

```text
{ transaction, alert_ids: [], forecast: Forecast }
```

`alert_ids`는 여전히 빈 배열입니다. 탐지·알림 연결은 추가하지 않았습니다.

## 재전송·동시 실행

거래 ID는 기존처럼 사용자 ID와 요청 UUID로 결정합니다. 완료된 거래가 있으면 금액·받는 사람·거래 종류가 원래 요청과 같은지 먼저 확인합니다. 같은 요청의 내용을 바꾸면 409입니다.

송금별 입력 스냅샷은 내부 실행 키 `transfer:<거래 ID>`를 사용합니다. 이 접두사는 송금 서비스 전용으로 예약합니다. 기존 `budget_input_snapshots.airflow_run_id`에 저장하므로 새 마이그레이션은 필요 없습니다.

완료된 요청 재전송은 이 키로 최초 스냅샷과 생활비 결과를 찾아 반환합니다. 이후 다른 송금이 있었거나 날짜·계산 버전·현재 준비 상태가 바뀌어도 다시 차감하거나 최신 잔액으로 과거 결과를 덮어쓰지 않습니다. 재전송 응답의 생활비는 **그 송금 당시 결과**이며 현재 상태는 최신 조회 API에서 읽습니다.

같은 사용자 행을 잠그므로 같은 토큰뿐 아니라 서로 다른 로그인 세션에서도 중복 송금·초과 출금을 막습니다. 기존 세션 → 사용자 → 계좌 잠금 규칙을 유지하고, 같은 세션에 오래 남아 있는 ORM 객체 대신 DB 상태를 다시 조회합니다.

기능 도입 전 완료된 거래에는 당시 생활비 입력이 없을 수 있습니다. 이 경우 재전송은 거래만 반환하고 `forecast`는 null입니다. 현재 잔액으로 과거 입력을 꾸며 만들거나 차감하지 않습니다. 새 기능으로 완료한 거래에 입력은 있으나 생활비 결과가 사라졌다면 503으로 안내하고 재차 송금하지 않습니다.

## 실패 시 롤백

잔액 변경·거래·송금 후 입력·생활비 결과를 같은 DB 트랜잭션에 저장합니다. 결과 계산이나 DB 저장, 응답 구성, 최종 commit에서 오류가 발생하면 rollback합니다. 이미 확정된 다른 거래·기존 결과는 보존합니다.

확정 전 오류는 503으로 안내하고 같은 요청 ID로 재시도할 수 있습니다. commit 응답 유실처럼 성공 여부가 불확실한 경우에도 같은 요청 ID를 사용해야 기존 확정 거래를 재조회할 수 있습니다. 새 요청 ID로 바꾸는 자동 재시도는 하지 않습니다.

## 검증

테스트용 pgvector PostgreSQL을 `DEMO_TEST_DATABASE_URL`에 지정하고 `backend`에서 실행합니다.

```powershell
..\.venv\Scripts\python.exe -m unittest tests.test_transfer_budgets tests.test_transactions tests.test_prepared_queries -v
```

신규 송금 연동 테스트 12개, 기존 송금 7개, 조회 11개를 검증합니다. 준비 누락·변경·날짜 경계, 송금 후 결과, 최초 결과 재전송, 다른 세션의 동시 요청, 실제 DB 오류, 최종 commit 실패, 기존 거래 호환을 포함합니다. 초기 준비·생활비 입력·계산·저장 회귀 테스트 53개도 별도로 검증했습니다.

테스트는 서비스 DB와 분리된 스키마에서 실행합니다. SQLite 인증·송금 단위 테스트는 PostgreSQL 전용 준비·생활비 연동을 명시적으로 대체하며 실제 DB 검증을 대신하지 않습니다.
